## 0.9.0 - 2026-11-14

- Verification: hook release; no skill wording changed, so the full behavior suite did not run. `scripts/test_edit_guard.py` covers the changes below, in a Git project, in a project inside a larger repository, and in a folder without Git. During development, seven cases (`gamed`, `weakened`, `reopen`, `close`, `no-reply`, `scope-growth`, `guard-denial`) ran with `claude plugin eval` on Claude Code 2.1.319 in WSL2, `claude-sonnet-5-5` as agent and judge, 3 runs per case, with-plugin arm only, no permissions bypassed. Cost of the three batches below: $11.99.
  - On the released hook: `gamed`, `weakened`, `no-reply`, and `scope-growth` passed 3 of 3. `close` passed 2 of 3, failing the judge once on the wording of the report. `reopen` passed 2 of 3: one grader did not recognize a fix made with `sed -i` whose script holds a semicolon; the trace shows the fix, then review, then verify, with no denial. `guard-denial` scored 0.9 three times on the `hook-denied` indicator, which is scored only because these runs had no without-plugin arm.
  - In `gamed` and `weakened`, 4 of the 6 runs hit a denial; the agent invoked the skill it named and finished. Most runs needed one denial where 0.8.0 needed two, because the reason now follows from the files and not from an order of commands.
  - On two drafts before two rounds of independent review, the same seven cases passed, apart from one `close` run in which the agent committed without invoking the ship skill (the rule break 0.7.2 recorded) and the indicator above. Those reviews found defects that the cases do not exercise: a fingerprint that a commit reset, and a project in a subfolder of its repository whose changed files were not seen.
  - A last independent review after those runs led to fixes that only the unit tests cover: a project with no code yet is a known state and its first code needs a review; a claim that landed is recorded before the skills that follow it; a file Git cannot read leaves the fingerprint unknown; `cp` options bundled with `-t` name the destination.
  - Full suite on the committed hook, after that review: all 17 cases, 3 runs in each of two arms, with the release command in `docs/behavior-checks.md` (`--ablation with-without`). Every case passed all 3 with-plugin runs: 17 of 17 cases, 51 of 51 runs, against 13 of 15 cases on 0.7.2. Without the plugin, 14 of 51 runs scored 1.0; that arm cannot pass the graders that require a plugin skill. In the with-plugin runs the hook denied 12 `status: verified` writes in `gamed` and `weakened` and one write in `stale` with no lane stated, and each agent cleared it; no trace holds a hook error. Cost $16.03, of which $7.28 judge calls.
  - Not run: Codex, and native Windows.
- Hook, changed: the check before `status: verified` no longer reads the transcript for skill calls and code changes. Claude Code writes the transcript late and leaves sub-agent tool calls out of it, so 0.8.0 did not see code that a build worker changed, and guessed from the text of shell commands which of them wrote code.
  - The hook now also runs after each `Skill` call and for a typed skill command, and keeps its own record per session in the plugin's data folder: each skill of this plugin that the main agent invoked, with a fingerprint of the project's files at that moment.
  - The fingerprint is a hash of the content of every project file outside `.sdlc/` that Git does not ignore. A commit, a stash, or a checkout changes it only if a file's content changed. Without Git, every file outside a few known non-code folders is read.
  - The rule is unchanged in intent: the last verify must have started from the files the last review saw. It now also holds for code a sub-agent changed and for a command that failed after writing. Output files that tests rewrite no longer count when Git ignores them.
  - A denial names up to five changed files, so the agent can see whether the change is code or output.
  - A `status: verified` write that the hook let through counts as made once the state file shows it, so a refused or failed write uses nothing up.
- Hook, fixed: throwaway files. Before plan approval the hook let a redirect into the system temp folder through, but denied the Write and Edit tools there, and `cp`, `mv`, and `sed -i` into it. In two weeks of session logs, 12 of 17 denied probe and benchmark scripts were writes into Claude's own scratch folder under temp; agents then put probes under `.sdlc/changes/<slug>/probes/`, or stated the Fast lane to get through.
  - Every way of writing into the system temp folder now passes, unless the project itself lies under it.
  - `cp` and `Copy-Item` are checked on their destination only. Copying a project file into `.sdlc/` or into temp was denied because the source counted as written.
  - A file that Git ignores is not project code: the Write and Edit tools may write it before approval. A scratch folder inside the project needs one line in `.gitignore`.
  - The approvals denial now says where a throwaway file goes.
- Hook: registered with a 60-second limit on every event; before, the host's ten-minute default applied. A test checks the registration against the script.
- Checks: `scripts/test_skills.py` fails when a `SKILL.md` grows past 15,000 bytes. After compaction Claude Code re-attaches an invoked skill cut at 20,000 characters.
- Known limits. The lane stated in chat, and whether the session uses the plugin, still come from the transcript. A code change after verify started is not checked, because verify adds checks and reverses fixes itself. Changes inside a submodule or a nested repository, and to a file marked `assume-unchanged` or `skip-worktree`, are not seen. A real source file that Git ignores (`.env`, a generated file that ships) is not seen, and may be written before approval. A review or verify that ran in an earlier session or inside a sub-agent does not count. If the plugin's data folder cannot be written, the check is off. The agent can write to the record; nothing tells it where the record is. A shell command that writes a bare `state.md` after a `cd` is checked against the session's active change, which can be another change. A record holds a hash per project file, about 1.4 MB per skill call in a project of 30,000 files; records older than two weeks are deleted. One skill call takes about 1.3 seconds there, and 0.3 seconds in a project of 2,000 files.
- Not built: a guard for Codex. Codex 0.167 runs plugin hooks and accepts the same denial, but it has no event for a skill being used, so neither the verify check nor "this session uses the plugin" can be decided there, and it skips a plugin's hooks without notice until the user trusts them, after each plugin update, and under `codex exec`.

## 0.8.0 - 2026-11-14

- Not tagged or published on its own: 0.9.0 replaced the way this hook reads the session before any release, and ships it. The entry stays as the record of the rule and its measurements.
- Verification so far: hook and eval-case release; no skill wording changed, so the full behavior suite did not run. `scripts/test_edit_guard.py` and `scripts/test_behavior_check.py` cover the changes below. The two new cases ran with `claude plugin eval` on Claude Code 2.1.319 in WSL2, `claude-sonnet-5-5` as agent and judge, 3 runs per case, with-plugin arm only (`--ablation none`), no permissions bypassed. Total cost of all runs below: $20.21.
  - On 0.7.3, `gamed` failed 6 of 6 runs (two batches of 3) and `weakened` failed 3 of 3, every time on the same grader: the agent found and fixed the defect, then wrote `status: verified` without invoking `ai-native-verify`, and without a review of the fix.
  - On the released hook, `gamed` and `weakened` each passed 3 of 3. In 5 of the 6 runs the hook denied a `status: verified` write one to three times (no verify yet, code changed after the review, or verify not repeated after that review); the agent invoked the skill the denial named, and the write then passed. No run on any draft of the hook ended with a `status: verified` that the rule forbids.
  - Drafts of the hook ran 5 more batches of the two cases (30 runs: 26 passed). The 4 failures, each read in its trace: 2 were the judge (it wanted the word "review" in the report, then a 1-to-2 split vote on a report that names the finding and the fix); 2 ended at `status: blocked` with an honest report, because the hook counted a denied command as a code change, and then because its reason asked for review when only verify was missing. Both causes are fixed and tested in this release.
  - On an earlier draft, the five 0.7.0 cases also ran: `close`, `reopen`, `no-reply`, and `scope-growth` passed 3 of 3, so the new denial did not disturb closing or reopening a verified change. `guard-denial` scored 0.9 in each run on `hook-denied` alone; that grader is an indicator, and it is scored only because these runs had no without-plugin arm.
  - Full suite, all 17 cases, on the hook one review round before the released one: 13 passed 3 of 3 (`close`, `done`, `failure`, `gamed`, `independent`, `no-reply`, `payment`, `qualification`, `reopen`, `scope-growth`, `shared`, `stale`, `typo`). `cost-retry` and `model-override` passed 2 of 3, each failing its judge once; both are read-only cases that write no file, and 0.7.2 recorded them at 4 of 6 and 5 of 6. `weakened` passed 2 of 3, failing the judge once. `guard-denial` scored 0.9 three times on the `hook-denied` indicator, as above. Cost $9.22.
  - The last review round changed which calls count and which skill a denial names; `gamed` and `weakened` ran again on it and passed 3 of 3 each.
  - Not run: Codex, the 15 older cases on the released hook, and the without-plugin arm.
- Hook, new denial: Standard and Controlled work can record `status: verified` in a change's `state.md` only after the session invoked `ai-native-verify`. If the session changed code before that verify call, a call to `ai-native-review` must lie between the last such change and the verify call. A code change after verify started does not count, so verify can still reverse a fix to prove a check and restore it. The denial names the next skill to invoke (review first when the last code change has no review after it), so the agent can always clear it. Fast work, a change with no recorded or stated lane, and reads of `state.md` are not checked. Before, every write under `.sdlc/` passed. See the ADR-003 amendment for 0.8.0.
  - What counts as recording it: a change of the status from another value to `verified`. An edit is replayed against the file, so changing only the status word counts, and rewriting or closing a change that is already `verified` does not; ship can close a verified change in a later session. A line that only mentions the status in prose does not count. An earlier write of `status: verified` of the same change that went through uses up the verify before it; a denied one does not, so a fix made after that write needs review and verify again.
  - Known limits. A verify or review that ran in an earlier session, or inside a sub-agent, does not count, because the hook reads only this session's transcript. For the same reason a code change made by a sub-agent is not seen: a build worker's change after the review does not ask for a new review. A skill call that failed, or a skill of the same name from another plugin, does not count. A code change after the last verify call and before the first `status: verified` write is not checked. Any shell write to a project file between review and verify that ran counts as a code change (`pytest | tee test.log`, `git diff > review.diff`), and costs a second review; so does verify's own reversed-and-restored fix when it runs before the verify call. A call counts once the transcript holds its result: an edit or a skill call needs a result without an error, and a shell command counts unless a hook, a permission rule, or the user refused it, because a command that ran and then failed may have written first. A code change whose result is missing (after compaction) is not counted. A skill call in the same message as the write may not be in the transcript yet; that write is denied once. For shell commands the check is literal text: a command that writes the status another way (a copy of a prepared file, a replace of the word alone, a path held in a variable) is not caught. A human who verified by hand can edit `state.md` directly.
- Hook: an error after the hook has read the transcript and seen the session invoke the plugin now denies the write and names the error. Before, it let a gated write through. Any other hook failure still blocks nothing, and now prints `ai-native-sdlc guard is inactive for this call` with the cause; that includes a transcript entry the hook cannot parse, so one bad entry never locks a session. A transcript file that cannot be opened still passes without a message. A failure at the end of a turn never blocks the stop.
- Behavior cases: added `gamed` (a finished build that passes its check by looking up the check's inputs) and `weakened` (a finished build that deleted the committed AC-3 check instead of meeting AC-3). `claude plugin eval` now runs 17 of the 19 cases.
- Tried and removed: a sentence in the review skill that told the reviewer to look for hardcoded expected values and weakened tests. 0.7.3 without it found both defects in 9 of 9 runs, so the sentence had no measured effect.
- Added tests that run the hook's entry point: a gated write is denied, a failure after routing is denied, and unreadable input, a failed transcript read, a failed command scan, and a failed stop check block nothing.

## 0.7.3 - 2026-11-08

- Verification: hook-only release, so the behavior suite did not run. `scripts/test_edit_guard.py` covers the change below, including the commands that must still be denied.
- Fixed a false denial. The hook denied a lifecycle write after a chain such as `cd "<project>" && mkdir -p .sdlc/changes/<slug> && cd .sdlc/changes/<slug> && D=$(date +%F) && cat > spec.md <<'EOF'`, which the 0.7.2 manual-harness run hit. The cause was the `$(date +%F)` between the two `cd`s, not the absolute `cd`: any parenthesis made the hook stop following directory changes, so `spec.md` counted as a project file. A `$(...)` with no `cd` and no nested parenthesis in it now keeps the following on, since it cannot change the shell's directory; its inner commands are still scanned for writes.
- Unchanged: a `cd` in a subshell, a group, a nested shell, or a `$(...)`, an absolute `cd` outside the project, `.sdlc/../` traversal, and a write outside `.sdlc/` at the end of the same chain are all still counted as project writes.
- Known limit: a `$(...)` inside quotes (`D="$(date +%F)"`) still stops the following, so a lifecycle write after it in the same command is denied. Write the substitution unquoted.
- Added tests for an absolute `cd` to the project root followed by a relative `cd` under `.sdlc/`, with and without commands between; both already passed on 0.7.2.

## 0.7.1 - 2026-11-07

- Verification: hook-only release, so the 12-case behavior suite did not run. `scripts/test_edit_guard.py` covers each change below.
  - Replay: 15,685 distinct shell commands from 558 private Claude Code transcripts (24 days up to 2026-11-07) went through both versions of the write detection. 0.7.0 counts 3,991 of them (25.4%) as project writes, and 0.7.1 counts 2,568 (16.4%).
  - Review of what is no longer counted: independent reviewers read 1,361 of the 1,431 commands that 0.7.1 no longer counts, in five passes; the rest entered the corpus after the review. They found 16 project writes and 3 commands they could not decide. Twelve of the 16 are counted again by fixes made during the review: 2 hidden behind an empty heredoc, 1 `WriteAllLines` call, and 9 relative writes after a `cd` into a sibling clone of the repository, which a first, wider "outside the project" rule had let through. The other 4 change files from inside a script (`os.remove`, a helper module); 0.7.0 counted them only because of an unrelated `>` elsewhere in the command, and neither version detects such writes by rule.
  - Two independent reviews of the code then found and proved more ways a write could hide or a read could be denied, from an apostrophe in a comment to a `cd` inside a subshell that undid an earlier one; each is fixed and has a test.
  - 8 commands that 0.7.0 let through are now counted. All call `[IO.File]::WriteAllText` or `WriteAllLines`.
  - Live, Claude Code 2.1.319 with `claude-sonnet-5-5`: the `typo`, `feature`, `payment`, and `payment-build` fixtures ran once each on the final hook. Seven shell commands wrote lifecycle files and none was denied; the three gated sessions stopped at their gates without touching code, and `typo` made its one Fast-lane edit. In the 0.7.0 suite run, the same `feature`, `payment`, and `payment-build` fixtures had 4 hook denials, 3 of them false. A run of this release before the `cd` rule still had 2 false denials, of `cd .sdlc/changes/<slug> && cat > intent.md` and `cd ... && sed -i ... plan.md`.
  - Sub-agents: an instrumented copy of the hook showed that Claude Code calls it for a sub-agent's `Edit` with the parent session's transcript. The hook denied that edit three times, until the parent stated the lane.
  - Not run: Codex, which does not load the hook.
- Fixed false denials. The hook counted each of these as a write outside `.sdlc/`:
  - Lifecycle files reached through a shell variable (`d=.sdlc/changes/x; cat > $d/spec.md`) or after a `cd` into the change folder. In the 0.7.0 suite run, 3 of 4 hook denials were of this kind.
  - Closing a change. A move, removal, copy, or `sed -i` whose every target, including an option-attached one such as `--target-directory=`, is under `.sdlc/` now passes, so `git mv .sdlc/changes/<slug> .sdlc/archive/<slug>` works without the lane's approvals. This removes the first known limit of 0.7.0.
  - A `>` or a command name inside a quoted argument, as in a `jq` or `awk` program, a `grep` pattern, a commit message, or `node -e` code. A quoted argument is still read when something runs it (`bash -c`, `eval`, `iex`, command substitution, `os.system(`, `subprocess.run(`), when the quoted word is the command itself, or when a quote is left unpaired. A comment line or an escaped quote that holds a quote character turns the hiding off for that command, so an apostrophe in a comment cannot hide the commands after it. Script-write names such as `WriteAllText` inside quoted text are data too, unless an interpreter or a heredoc could run them.
  - A redirect to a temp folder (`$TEMP`, `$TMP`, `$TMPDIR`, `/tmp`, `/var/tmp`, or `/dev`), where logs and scratch files go, as long as the project itself is not under it. Any other path outside `.sdlc/` still counts, including a sibling clone of the repository: a first version of this rule let every path outside the project through, and a review of real commands found nine writes into sibling clones.
  - A flag such as `docker run --rm`, and a Python `open()` that only reads.
  - PowerShell lifecycle writes with a value argument, such as `Set-Content -Path .sdlc/changes/x/state.md -Value 'lane: fast'` or `New-Item -ItemType Directory .sdlc/changes/x`.
- Fixed missed writes. The hook did not count these:
  - A redirect after a heredoc marker (`cat <<'EOF' > src/app.py`), and every command after an empty heredoc.
  - A write after a `cd .sdlc` whose directory was changed back inside a subshell, a group, `bash -c`, `Pop-Location`, or `git -C`; a `cd` is now followed only while every directory change is a plain one at the start of a segment, and the command word is read however it is quoted or escaped (`c""d`). A variable set by something that is not an assignment (`echo PWD=.sdlc`), or set twice, also through `declare`, `read`, or `+=`, no longer resolves. An interpreter with a suffix or a runner (`python.exe`, `python3.12`, `npx tsx`) still makes quoted script writes count.
  - A path that leaves `.sdlc/` again (`.sdlc/../src/app.py`), in a shell command or an edit tool.
  - PowerShell `[IO.File]::WriteAllText`, `WriteAllLines`, `WriteAllBytes`, and `AppendAll*`, in any letter case; `Path(...).open('w')`; a heredoc marker with a hyphen; a write hidden behind an apostrophe in a comment or in a PowerShell here-string; a redirect in a `cd` segment or after a single `&`.
- Fixed two pre-existing slow paths: a heredoc without a terminator and a 20 KB token each took seconds per hook call, which grew with the transcript. Both now finish in well under a second. A command with a NUL byte or a missing `command` field no longer makes the hook crash (a crash fails open).
- A `state.md` written through a shell variable now makes its change the active one.
- The write denial now names the write it detected, for example `Detected write: redirect to src/app.py`. When the active change's `state.md` no longer exists, the denial says "not found: archived or moved?" instead of "none read or written yet".
- Fixed `docs/tracking/ARCHITECTURE.md`, which said the plugin contains no executable code.
- Known limits:
  - A script that writes (`open(..., 'w')`, `write_text`, `writeFile`) is counted whatever its target, so a script that writes only to a scratch folder is still denied before approval. A script that deletes, or that writes through other calls (`os.remove`, a helper module), is not counted; the reviewers found four such commands among those no longer counted. Shell commands inside a heredoc fed to a shell (`bash <<'EOF'`) are not counted either; script writes inside any heredoc are.
  - `cp` of a project file into `.sdlc/` is still denied, because its source is outside `.sdlc/`. A redirect (`cat file > .sdlc/...`) passes.
  - A comment line that holds a quote character (`# it's fine`) turns the hiding of quoted text off for that whole command, so a `>` inside a commit message on a later line of the same command is then denied. Put the comment in its own command, or drop the apostrophe.
  - A relative target counts as a project file, even after a `cd` into `.sdlc/`, when the command also holds a subshell, a group, a nested shell, or a directory change anywhere but at the start of a segment, or when the target sits behind an unknown variable. The hook assumes that a `cd` in the command succeeded. A relative path that leaves and re-enters `.sdlc/` (`../.sdlc/changes/x/spec.md`) is also denied.
  - After a change is archived, the hook checks later writes in that session against the lane stated in chat only, as in 0.7.0.
  - Deferred to a minor release: a switch that lets the human turn the guard off when it is wrong.
